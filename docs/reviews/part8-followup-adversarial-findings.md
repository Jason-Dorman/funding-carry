# Adversarial review of the Part 8 follow-up — raw findings

**Run:** 2026-09-19 · eight lenses over the diff that applied the PO's five Part 8 decisions, every finding attacked twice · **51 raw findings, 34 distinct after merge, all 34 verified: 15 survived, 19 refuted.** Four needed a tiebreak.

This is the second review of Part 8. The [first one](part8-adversarial-findings.md) named five gaps for the PO rather than guessing them; the PO decided all five on 2026-09-19, and this run reviews the diff that applied those decisions — including whether applying them broke anything the first review had fixed. It had not: the four Part 8 fixes that could have regressed (round-trip suppressed for adopted orders, `REJECTED` bounded in `closedOut`, `Track` completing an adopted order, the no-signal-race report handoff) were checked individually and are intact.

**Method, same bar as last time and no cap this time.** Eight lenses, each attacking one seam of the change set: the redefinition of `Overdue`, the arithmetic of the two new gauges, the new goroutine and the shutdown order, whether the `FIX_TARGET` check really binds the order path, mutation-testing every new behaviour, doc lockstep in both directions, what deleting `Forget` left behind, and whether the gauges can settle `ORDER_TIMEOUT` at all. Duplicates across lenses are merged with the merge count kept. **Every** distinct finding then got two independent skeptics with different methods — one reads the code and the documented contract, one copies the repository and runs an experiment — both told to default to *refuted* when unsure, and where they disagreed a third did both methods and had to name the specific mistake one of them had made. The [Part 7 run](part7-adversarial-findings.md) left 14 of 30 findings unverified and the [Part 8 run](part8-adversarial-findings.md) verified all 33; this one verified all 34.

**Fourteen of the fifteen survivors are fixed**, each with a regression test run against the unfixed code and watched to fail first. The fifteenth is not a code defect but a broken promise; the documentation half was fixed here and the instrument half went to the PO, who closed it two days later with [CHANGE-002](../CHANGE-002-ack-latency-histogram.md).

## The one that mattered most

`adopt` creates a tracker record before `transition` has decided whether the report that caused it is even applicable. That was reported in the Part 8 review and **refuted** there, on two grounds that were true at the time: `Tracker.Forget` existed, and `Open()`/`Overdue()` had no production caller, so a phantom record was inert. This diff removed both grounds in the same session — `Forget` was deleted as dead code, and the two new gauges made `Open`/`Overdue` production readers — and the inert finding became a live one.

A single malformed ExecutionReport for an unknown ClOrdID — a `PARTIAL` that filled nothing, or an `OrdStatus` the machine has no rule for, both of which parse cleanly off the wire — left a record in `PENDING` that no report can move and nothing can remove. Under the new definition of overdue, `PENDING` past its deadline **is** overdue, so that one message pins `carry_orders_open` and `carry_orders_overdue` at ≥1 for the life of the process: the alert in architecture §8 fires forever, the one series api-spec §6 points Part 15 at is poisoned forever, and the router that reads it is told, forever, to unwind the other leg of an entry for an order that exists at no venue.

The regression test fails against the unfixed code on all four first-report shapes it covers, printing the phantom:

```
--- FAIL: TestARefusedFirstReportLeavesNoOrderBehind
    the refused report left a phantom order behind
    1 open orders after a refused report: [{ClOrdID:A1 Qty:0 State:PENDING ... Adopted:true}]
    carry_orders_open = 1, want 0
    carry_orders_overdue = 1, want 0
```

The fix is that **a report which is not applied undoes its own adoption**. The report is still counted and still logged — refusing it is not forgetting that it arrived — but it leaves nothing behind. That also makes true a sentence the diff had written and the code did not support: only a pending order can be overdue, and a pending order is always one this process submitted.

The lesson is narrower than "the earlier refutation was wrong": it was right, and it expired. A refutation that rests on *"nothing reads this yet"* has a shelf life exactly as long as that sentence stays true, and the diff that makes something readable is the diff that has to re-run the refutation.

## The one that was open for the PO — now closed

> **Resolved 2026-09-21 by [CHANGE-002](../CHANGE-002-ack-latency-histogram.md):** the ack-latency histogram was added (`carry_order_ack_seconds`, with `carry_order_ack_timeouts_total` for the orders that never come back), and 30 s is retained until paper trading produces data. The section below is kept as the evidence that prompted it.

**The two new gauges cannot produce the `ORDER_TIMEOUT` value they were added to produce.** That claim was made in four places (api-spec §6 and §7, the build-plan gap table, `.env.example`, and twice in code comments), and the review measured it rather than argued it:

- Prometheus scrapes every 15 s (`deploy/prometheus/prometheus.yml`). An acknowledgement that arrives just past a 30 s deadline raises the gauge for a second or two, so most scrapes never see it — the *tighter* the miss, the more invisible it is, which is the opposite of what the docs promised.
- A gauge carries a count, not a latency. An ack at 31 s and an ack at 45 s are the same observation, so no series of these values contains the number that should replace 30 s.
- The distribution exists and is thrown away: `acknowledged()` holds both `cur.SubmittedAt` and the report's own time and observes nothing. The only histogram, `carry_order_roundtrip_seconds`, measures submit-to-*terminal* and skips adopted orders entirely.

Every overstated claim has been corrected to what the gauges actually do — they show *that* the deadline is being missed, and they catch a venue that has stopped answering. What was left was a decision for the PO rather than the agent: add an ack-latency histogram, or accept that `ORDER_TIMEOUT` stays a chosen number. **The PO chose the histogram** — see [CHANGE-002](../CHANGE-002-ack-latency-histogram.md), which also records the three places the implementation departed from the directive's letter and why. Part 15's 24 h soak is the measurement window, and it carries the deliverable and an acceptance item saying so.

## Notable refutations

Nineteen findings died, and four of them are worth reading:

- **"The `FIX_TARGET` check constrains a comp id, not a network address."** True as a mechanism — `FIX_HOST` and `FIX_PORT` are unvalidated — and refuted as an indictment. The experiment showed a counterparty that does not answer to `SenderCompID=SIMV` cannot complete a logon at all: logon, EOF, reconnect, no NewOrderSingle, non-zero exit. Reaching a venue holding real funds would take an acceptor deliberately impersonating the simulator. Both skeptics also noted that all three doc sentences name `FIX_TARGET` as the mechanism in the same breath, one of them saying the counterparty "calls itself" SIMV — the docs claim exactly what the code does.
- **"The new `Overdue` makes a dead-but-acknowledged order invisible."** The mechanism is real and intended. What killed it: architecture §6.4's leg rule says the perp leg "cannot be **placed** within a timeout", and an unacknowledged order is precisely one that could not be placed — the narrowed definition implements that rule rather than orphaning it. The experimenter also found that reverting the predicate leaves the only order-submitting path in the tree byte-identical, so the diff removed no working protection.
- **"`overdue > open` can be read in a single scrape during steady state."** Both skeptics disagreed and the tiebreaker built the proposed fix and ran it: it removes no staleness from the overdue series and introduces a *new* wrong reading in the open one. The shutdown-window version of the same skew, where the watcher was dead while the drain was still running, survived separately and is fixed.
- **"The floating comment where `Forget` used to be is invisible to godoc."** Confirmed as a fact and refuted as a defect: `gofmt -l`, `go vet` and `golangci-lint run` are all clean, and the retention decision is recorded in api-spec §3.2 and the build-plan where a reader looks for it.

One refuted finding still produced a fix, as in the Part 8 run: the claim that nothing alerts on `carry_orders_overdue` was refuted (no alert rules file exists yet for *any* series — that is Part 19), but architecture §8's new row now says what the gauge can and cannot tell an operator, so the row does not promise a precision the series lacks.

## What this run cost, and what it is worth

81 agents, ~5.4M tokens, 30 minutes wall clock. It found one defect that would have fired a false risk signal for the life of a process, one shutdown window that published an arithmetically impossible pair of gauges, one binary using a word for the meaning the PO had just deleted, four pieces of documentation asserting things the code does not do, and five behaviours whose tests could not fail — in a 259-line diff that had already been written carefully and had a green suite.
